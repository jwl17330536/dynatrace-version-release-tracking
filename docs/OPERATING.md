# Operating Guide

## Compliance Baseline
Follow the SE Field Asset Library CONTRIBUTING requirements.

## Required Checks Before PR
1. Asset tested in a live Dynatrace environment.
2. No duplicate asset already exists in target library path.
3. No credentials, API tokens, or customer-confidential data in files.
4. Metadata complete (meta.yaml required fields).
5. README includes setup and usage instructions.
6. Dashboard and notebook assets shared with Use Case Playground User group.
7. Validation suite passes, including release lookup enrichment checks.

## Validation Guardrails
- Run `python3 scripts/run_validation_suite.py --profile all` before PR or deployment.
- For automation/CI parsing, use `python3 scripts/run_validation_suite.py --json`.
- For canonical install artifact validation (v10), use `python3 scripts/run_validation_suite.py --profile canonical`.
- For faster v5-only verification, use `python3 scripts/run_validation_suite.py --profile v5`.
- For CI-safe static checks without tenant credentials, use `python3 scripts/run_validation_suite.py --profile ci-static --json`.
- For one-command preflight report generation, use `python3 scripts/run_v5_preflight.py`.
- For CI-safe preflight report generation without live validators, use `python3 scripts/run_v5_preflight.py --profile ci-static`.
- For local emulation of the static GitHub Actions job, use `bash scripts/run_ci_static_smoke.sh`.
- For local emulation of the manual live GitHub Actions job, use `bash scripts/run_ci_live_smoke.sh` with `DT_ENVIRONMENT` and `DT_API_TOKEN` exported.
- Prefer `bash scripts/run_ci_smoke.sh <mode>` as the single entrypoint for local static/live/preflight runs.
- Prefer `make` aliases for day-to-day use: `make static`, `make live`, `make preflight PROFILE=ci-static`, `make ci-check`.
- Use `make release-readiness` to run `ci-check` + ci-static preflight and produce readiness artifacts.
- To include a live workflow run in preflight, use `python3 scripts/run_v5_preflight.py --execute-workflow`.
- GitHub Actions workflow `.github/workflows/release-tracking-validation.yml` runs `ci-static` on PR/push and supports optional live `v5` checks via manual dispatch.
- CI workflow uploads `reports/validation/` artifacts and writes run summaries even when validation fails.
- Run summaries are generated by `scripts/write_validation_summary.py` for both CI and local smoke flows.
- Local live smoke configures and uses a readonly `dtctl` context `ci` before running live checks.
- The suite now includes `scripts/validate_release_lookup_enrichment.py`.
- The suite now includes `scripts/validate_v5_contract_static.py`.
- The suite now includes `scripts/validate_release_tracking_v5_e2e.py`.
- The suite now includes `scripts/validate_dashboard_layout_parity.py`.
- The suite now includes `scripts/validate_v5_actionable_tiles.py`.
- The suite now includes `scripts/validate_canonical_assets.py` for canonical v10 artifact checks.
- Query smoke tests run for both `release-tracking-dashboard.v4.json` and `release-tracking-dashboard.v5.json`.
- v4/v5 query and layout checks are retained as legacy compatibility gates for contributor regression detection.
- Static contract validation requires workflow v5 to publish guidance fields (`risk_priority`, `highlight_focus`, `action_hint`) and dashboard v5 queue/risk tiles to reference expected actionable output columns.
- End-to-end v5 contract validation verifies workflow tokens, lookup enrichment presence, dashboard actionable tile outputs, and layout parity in one gate.
- Preflight runner writes machine-readable and human-readable artifacts by default:
	- `reports/validation/v5-preflight.latest.json`
	- `reports/validation/v5-preflight.latest.md`
- Release-readiness runner writes both timestamped and latest artifacts:
	- `reports/validation/release-readiness.<timestamp>.json`
	- `reports/validation/release-readiness.<timestamp>.md`
	- `reports/validation/release-readiness.latest.json`
	- `reports/validation/release-readiness.latest.md`
- v5 actionable tile validation requires Queue/Risk tiles to expose populated operator fields (`action`, `risk_priority`, `recommended_action`, `triage`, `risk_summary`, `highlight_summary`, `release_notes_url`).
- Enrichment validation requires latest rows to include populated values for:
	- `risk_priority`
	- `highlight_focus`
	- `action_hint`
	- `release_url`
- Layout parity validation requires v5 tile layouts to match the v4 baseline layout (live export when present, otherwise v4.json fallback).
- This guardrail protects dashboard usability by preventing silent regressions in the workflow-generated lookup schema.

## Versioning Rules
- Workflows: vN naming, one active scheduled version.
- Dashboards: vN naming, no in-place edits on prior versions.
- Keep previous versions for rollback unless explicitly decommissioned.
- Workflow JSON must retain a stable `id` so `dtctl apply` updates the same resource instead of creating duplicates.

## Token/Secret Handling
- Use Credential Vault IDs in workflow scripts.
- Never commit secret values.
- Use placeholders for environment-specific identifiers.

## Data Source Strategy
- Current runtime distribution: live telemetry where available.
- Release metadata and next rollout visibility: workflow-built lookups.
- Fallback: explicit Not yet published when no future release is documented.
